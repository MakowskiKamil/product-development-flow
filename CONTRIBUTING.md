# Contributing

Issues and pull requests are welcome. The maintainer reviews and merges every PR. There is no promised response time: this is a one-maintainer project, developed in the open, and the roadmap is private (planned work lives in the maintainer's Linear, not in this repo).

## What is likely to land

- Bug fixes, with a test that fails before the fix.
- Docs: a README step that did not work as written, a missing troubleshooting entry.
- Playbook examples: a playbook for a workflow `playbooks/example/` does not cover, named after the workflow, never after a real repo, person or workspace.

A larger change (a new command, a change to the role briefs or the keeper's rules) is better opened as an issue first, so you do not write code that does not fit the spec it would change.

## How a PR should look

- Small and focused: one change per PR, with its tests in the same PR.
- No dependencies. Node.js ≥ 22, ES modules, `node --test`. Shell out with `child_process.execFileSync` and an argument array, never a shell string.
- `roles/*.md` and `lib/` stay repo-agnostic: repo names, paths, ports and workspaces belong in playbooks.
- Read [CLAUDE.md](CLAUDE.md): it is the rule set the maintainer's own sessions follow. Its tech-stack, test and branch rules hold for PRs too; its Linear and gstack steps are the maintainer's, not yours.

## Tests

```sh
npm test
```

It must be green and exit 0. Tests never start a real session: they use the fake claude in `test/fixtures/`, a temp state dir and a temp `~/.claude` (see `test/helpers.mjs`).

Every test states its card in three comment lines directly above it, and a test without them fails the suite:

```js
// protects: the observable behavior this test keeps true
// fails_when: the wrong result it rejects
// no_claim: what a green run does not prove
test("…", () => { … });
```

After changing a role brief, regenerate the expected cards with `FLOW_UPDATE_FIXTURES=1 npm test` (it fails on purpose after rewriting them), read the diff of `test/fixtures/cards/`, run `npm test` again without the variable, and commit the cards with the change.

### The private-terms guard

`test/private-terms.test.mjs` fails when a term from the maintainer's private list appears in a file or path of the repo. The list lives outside the repo, because the list is itself private: locally a file (`~/.product-dev-flow/private-terms.txt`, or `FLOW_PRIVATE_TERMS_FILE`), in CI the repository secret `PRIVATE_TERMS`. Without the list, the guard is reported as skipped, never as a pass.

If CI reports it skipped on your fork, that is expected; a hand-started run is red on a fork, that is the maintainer-only path.

What the guard is: a net, not a lock. On the maintainer's machine it runs inside `npm test` before every commit, where it prevents a leak. In CI it is a second net for the maintainer's branches and `main`, for the case that a session skipped the local run or ran it before the list existed. It never runs on fork PRs, and a term on a pushed branch is already public when CI reports it.

### The compatibility fixture

`test/compat.test.mjs` runs today's `flow tree --all` and keeper `--dry-run` on `test/fixtures/state-b913f36/`, a state dir written by an older `flow` (commit b913f36 of the maintainer's private history), and compares the output with two expected files. Those files are frozen snapshots, not test output to refresh:

- They are regenerated by hand, on the maintainer's private copy of the old history, when the question is the shape of old records.
- Or by the new code, only in a PR that changes `lib/tree.mjs` or the keeper's log wording, with the diff of the expected files shown in the PR and reviewed as a rendering change.

Any other failure of this test means today's code reads old state differently: fix the code, or say in the PR what happens to state written before your change. See `test/fixtures/state-b913f36/README.md`.

## The maintainer's rule for pulling `main`

The maintainer's own sessions run `flow` and the keeper from a checkout of this repo, so a merge reaches them only when that checkout pulls. The checkout pulls `main` only at a quiet moment (no session mid-merge or mid-release), then runs `flow tree` and `node keeper/flow-keeper.mjs --dry-run` and compares them with the output from before the pull; on any difference it goes back to the previous commit. The compatibility test above is the permanent gate that a merge keeps old state readable.
